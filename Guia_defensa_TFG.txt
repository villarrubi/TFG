Esta guía no sustituye a la memoria. Su función es convertir el proyecto en una explicación defendible: primero fija la idea central, después recorre el flujo técnico real y, por último, prepara respuestas honestas para las preguntas difíciles.

Tesis del trabajo: es viable reunir en una única aplicación web un detector explicable basado en reglas y un clasificador neuronal entrenable. La heurística aporta trazabilidad; el modelo aprende patrones; el modo combinado equilibra ambos. El prototipo demuestra integración y funcionamiento, no sustituye a una plataforma empresarial de seguridad.


La idea central que debes defender

El problema no es solamente reconocer palabras como 'urgente' o 'contraseña'. El phishing combina suplantación técnica, manipulación psicológica y enlaces o adjuntos preparados para inducir una acción. Por eso un detector basado en una sola señal es frágil: una regla fija puede ser muy explicable pero no generaliza bien, mientras que un modelo estadístico puede reconocer patrones menos obvios pero resulta más opaco.

La propuesta del TFG es una aplicación web local y autocontenida. Streamlit organiza la interacción y llama directamente a módulos Python que parsean el correo, construyen señales, calculan el riesgo y ejecutan el clasificador. No existe una API de análisis separada en el alcance que se defiende. Gmail y Telegram son integraciones externas opcionales; no son clientes de un backend propio.

Frase de apertura: Mi trabajo diseña y evalúa una aplicación web para analizar correos sospechosos mediante dos perspectivas complementarias: reglas explicables sobre cabeceras, contenido, HTML y URLs, y un clasificador neuronal TF-IDF + MLP entrenable en español e inglés.


Qué problema resuelve

	•	Permite analizar un correo sin abrir sus enlaces ni ejecutar sus adjuntos.

	•	Convierte cabeceras y estructuras difíciles de interpretar en señales comprensibles.

	•	Ofrece una puntuación común de 0 a 100 y tres modos: heurístico, neuronal y combinado.

	•	Facilita trabajar con texto pegado, archivos .eml o mensajes autorizados desde Gmail.

	•	Permite entrenar y evaluar modelos desde la misma interfaz web.

	•	Puede revisar periódicamente Gmail y enviar una alerta por Telegram, de forma opcional.

Qué no pretende resolver

El prototipo no es un filtro corporativo completo, un antivirus, un sandbox de adjuntos ni una pasarela de correo. No navega por las URLs, no consulta reputación en tiempo real, no valida certificados TLS, no ejecuta código HTML y no bloquea mensajes en Gmail. Tampoco ofrece autenticación multiusuario o aislamiento de sesiones para un despliegue público.

Respuesta madura: delimitar el alcance no debilita el proyecto. Demuestra que se conoce la diferencia entre un prototipo académico verificable y un producto de seguridad listo para producción.

Apertura sugerida

El phishing sigue siendo eficaz porque no ataca únicamente a la tecnología: explota la confianza, la urgencia y la apariencia de legitimidad. Mi TFG parte de esa idea y desarrolla una aplicación web que analiza correos desde dos puntos de vista. El primero es heurístico y explica qué indicios técnicos o psicológicos aparecen. El segundo es un clasificador neuronal que aprende patrones de ejemplos etiquetados. Ambos pueden usarse por separado o combinarse para producir una puntuación de riesgo única.

Cierre sugerido

El resultado es una base funcional, explicable y extensible. El valor del trabajo no está en afirmar que se ha resuelto por completo la detección de phishing, sino en demostrar un flujo reproducible que integra análisis estático, aprendizaje supervisado, Gmail y una interfaz web, y en identificar con precisión qué mejoras serían necesarias para llevarlo a un entorno real.

Arquitectura web y organización del sistema

Idea clave: Streamlit actúa como capa de presentación y orquestación. La lógica de análisis vive en módulos Python reutilizables y se invoca mediante llamadas locales. Técnicamente Streamlit sirve una página al navegador, pero no existe un backend REST independiente diseñado por el proyecto.


Usuario
  -> Streamlit: Inicio / Configuración / Detección / Monitor / Entrenamiento
      -> Entrada: texto | EML | Gmail API (OAuth, solo lectura)
          -> Parser y normalización: CorreoAnalizado
              -> Rama heurística: señales -> pesos -> explicación
              -> Rama neuronal: idioma -> TF-IDF -> MLP -> probabilidad
          -> Modo elegido: heurístico | neuronal | combinado
      -> Resultado en Streamlit y, si procede, alerta por Telegram

Por qué esta separación es importante

	•	Responsabilidad única: SignalBuilder decide señales, RiskScorer calcula riesgo y ExplanationBuilder redacta explicaciones.

	•	Sustitución: se puede cambiar el modelo neuronal sin reescribir el parser o la interfaz.

	•	Pruebas: cada componente puede validarse con entradas controladas.

	•	Reutilización: la detección manual y el monitor comparten las mismas piezas de dominio.

	•	Mantenibilidad: una regla nueva se añade en el módulo adecuado y después se registra en SignalBuilder y RiskScorer.

Por qué Streamlit

Streamlit reduce el trabajo de frontend y permite dedicar el TFG al motor de análisis. Sus widgets, pestañas, tablas, métricas y estado de sesión son suficientes para construir una demostración interactiva en Python. La contrapartida es que cada interacción vuelve a ejecutar el script y que el framework no aporta por sí solo autenticación, control multiusuario ni aislamiento de datos. Por eso es apropiado para un prototipo académico local, pero no basta para publicar el sistema como servicio abierto.

Flujo completo de un análisis

El recorrido siempre intenta llegar a la misma representación interna. Esto evita que las reglas tengan que saber si el mensaje vino de un cuadro de texto, de MIME o de Gmail.

	1.	El usuario elige el origen del correo y el tipo de análisis.

	2.	La entrada se convierte en texto o en un diccionario estructurado con remitente, asunto, cuerpo, HTML, cabeceras, URLs, anclas y adjuntos.

	3.	CorreoAnalizado.from_input normaliza el formato y reúne las URLs del texto y de los href HTML.

	4.	SignalBuilder ejecuta 28 reglas agrupadas por identidad, autenticación/URLs, contenido y HTML/adjuntos.

	5.	RiskScorer suma los pesos activos, multiplica por 100 y limita el resultado al rango 0-100.

	6.	ExplanationBuilder genera una frase legible por cada señal evaluada.

	7.	Si el modo usa el clasificador, langdetect selecciona español o inglés en la vista de detección y se carga el .joblib correspondiente.

	8.	TF-IDF transforma el texto en un vector numérico y MLPClassifier devuelve una probabilidad de phishing.

	9.	En modo combinado se calcula una media ponderada; por defecto 60 % heurística y 40 % red neuronal.

	10.	La interfaz muestra veredicto, porcentaje, señales, enlaces y cabeceras. El monitor puede además registrar el ID de Gmail y avisar por Telegram.

Qué datos conserva el resultado

La salida heurística es un diccionario estable con is_phishing, risk_score, signals, urls, anchors, headers, html_body, from, subject y explanation. Mantener esta forma estable desacopla la interfaz de los detalles internos. El resultado neuronal es más pequeño: clasificación, puntuación, descripción, remitente y asunto. En el combinado se conserva el contexto y las explicaciones de la rama heurística.

Matiz importante: la explicación del modo combinado describe las señales heurísticas; no explica qué n-gramas impulsaron la probabilidad del MLP. Por tanto, el sistema es explicable en su componente de reglas, pero no ofrece explicabilidad completa del modelo neuronal.

Parseo MIME

analizador_email.py usa BytesParser con policy.default. Si el mensaje es multipart, recorre sus partes y conserva el primer cuerpo text/plain, el primer text/html y los nombres de los adjuntos. Si solo existe HTML, extrae el texto visible para que el clasificador pueda analizarlo. También obtiene las anclas <a>, sus href y el texto mostrado, lo que permite detectar enlaces cuyo destino no coincide con lo que ve el usuario.

La representación plana incluye From, Reply-To, Subject y cuerpo. Es una simplificación deliberada: algunas reglas buscan cabeceras adicionales en full_text, de modo que un EML cuyo full_text no incluya Authentication-Results, Return-Path o Received puede perder señales que sí estaban en el diccionario headers. Esta es una mejora técnica razonable: incorporar todas las cabeceras relevantes al texto normalizado o hacer que las reglas consulten directamente headers.

Gmail como origen

gmail_client.py solicita únicamente el alcance gmail.readonly. El flujo OAuth carga credentials.json, abre el consentimiento local la primera vez y guarda token.json. Después lista mensajes con una query de Gmail, descarga cada mensaje en formato raw, corrige el padding base64url y reutiliza exactamente el parser EML. El sistema no borra, etiqueta ni modifica mensajes.

Motor heurístico

La heurística convierte conocimiento experto en indicadores booleanos. No intenta demostrar que una señal aislada sea phishing; acumula evidencia. Esta decisión es importante porque muchos comportamientos también aparecen en correos legítimos: un Reply-To distinto puede ser una plataforma de marketing, un acortador puede ser inocuo y un mensaje urgente puede ser real.

Familias de señales

Autenticación y ruta	SPF, DKIM, DMARC, Received.	Fallos de autenticación y rutas de entrega anómalas.

Cómo se calcula el riesgo

Cada señal activa aporta un peso. La suma se multiplica por 100 y se limita entre 0 y 100. Los 27 pesos positivos suman 1,97; por tanto, varios indicadores pueden saturar la puntuación y el límite evita superar 100. La firma o cifrado S/MIME/PGP resta 0,03, porque constituye una evidencia débil de autenticidad, nunca una garantía.

riesgo_heurístico = clamp(100 * suma(peso_i * señal_i), 0, 100)
phishing_heurístico = riesgo_heurístico >= 45

El umbral 45 es una decisión operativa del prototipo. No procede de una calibración estadística exhaustiva y debe presentarse como parámetro ajustable. Para producción habría que optimizarlo con una curva precision-recall y con costes explícitos de falsos positivos y falsos negativos.

Qué aporta la explicabilidad

ExplanationBuilder genera una explicación positiva o negativa para cada señal, en el mismo orden que SignalBuilder. El usuario no recibe solo 'phishing/no phishing': puede revisar qué cabecera falló, si hubo un dominio extraño o si el HTML contenía un formulario. Esta trazabilidad permite corregir reglas, discutir falsos positivos y justificar el resultado durante la defensa.

Clasificador neuronal

La segunda rama aprende patrones a partir de correos etiquetados. No recibe directamente una lista de señales: recibe texto y aprende qué términos o combinaciones suelen asociarse a phishing o correo legítimo.

TF-IDF: convertir texto en números

TfidfVectorizer asigna peso alto a términos que son frecuentes en un correo pero no aparecen en todos los correos. Los unigramas capturan palabras individuales y los bigramas expresiones como 'verifica cuenta' o 'pago pendiente'. strip_accents='unicode' reduce variaciones ortográficas. En español se usa una lista local de stopwords; en inglés, la lista incluida en scikit-learn.

La configuración por defecto limita el vocabulario a 3.000 características, acepta términos que aparezcan al menos una vez y usa n-gramas de 1 a 2. Es un compromiso entre memoria, velocidad y capacidad. Un vocabulario demasiado pequeño pierde información; uno muy grande aumenta ruido y riesgo de sobreajuste.

MLP: clasificar la representación

MLPClassifier recibe el vector TF-IDF. La configuración actual usa dos capas ocultas de 64 y 32 neuronas, activación ReLU, regularización L2 alpha=0,0001, learning rate inicial 0,001, hasta 500 iteraciones y semilla 42. La salida predict_proba se interpreta como probabilidad de la clase phishing; el modo neuronal considera phishing cuando la probabilidad es al menos 0,5.

Parámetro	Valor	Función
n-gramas	(1, 2)	Palabras y parejas de palabras.
max_features	3.000	Límite del vocabulario TF-IDF.
capas ocultas	(64, 32)	Capacidad del perceptrón multicapa.
activación	ReLU	Introduce no linealidad.
alpha	0,0001	Regularización para contener el sobreajuste.
learning rate	0,001	Tamaño de los pasos de optimización.
max_iter	500	Límite de iteraciones de entrenamiento.
random_state	42	Reproducibilidad del componente aleatorio.


Entrenamiento y persistencia

El pipeline reúne vectorizador y MLP en un solo objeto. Se entrena con fit, se predice con predict o predict_proba y se guarda completo con joblib. Hay un archivo para español y otro para inglés. ModelStorage encapsula la existencia, carga y guardado; si el fichero falta o no puede deserializarse devuelve None, lo que activa el fallback.

La aplicación conserva dentro del modelo los textos y etiquetas de entrenamiento, las fuentes, columnas, fecha, hiperparámetros y estadísticas. Esto facilita reentrenar y mostrar metadatos, pero aumenta el tamaño del .joblib y puede conservar texto sensible. Para producción sería mejor separar el artefacto de inferencia de los datos de entrenamiento.

Modelos guardados en la rama

Modelo	Datos acumulados	Distribución	Exactitud de entrenamiento
Español	1.298 ejemplos	686 phishing / 612 legítimos	99,85 %
Inglés	164.971 ejemplos	85.781 phishing / 79.190 legítimos	99,98 %


No confundas métricas: esas exactitudes se calculan sobre los mismos datos usados para entrenar. Sirven como comprobación de ajuste, no como evidencia de generalización. Una cifra cercana al 100 % puede indicar memorización y exige evaluación separada.


Por qué TF-IDF + MLP y no un transformer

La elección es coherente con el alcance: requiere menos recursos, se entrena localmente, permite experimentar con CSV propios y ofrece una línea base comprensible. Un transformer podría captar mejor contexto y semántica, pero aumentaría coste, complejidad de despliegue y necesidad de datos. La respuesta correcta no es que MLP sea mejor que un transformer, sino que es una solución proporcional al objetivo académico y deja una comparación futura bien definida.

Modo combinado

El modo combinado calcula una media ponderada de las dos puntuaciones. En la interfaz, el usuario elige el peso heurístico y el peso neuronal se deriva como 100 menos ese valor, evitando configuraciones que no sumen 100.

riesgo_combinado = (riesgo_heurístico * peso_heurístico + riesgo_neuronal * peso_neuronal) / (peso_heurístico + peso_neuronal)
configuración habitual: 60 % heurística + 40 % neuronal
umbral habitual del combinado: 45

El resultado es una puntuación de riesgo, no una probabilidad calibrada. Mezcla una suma experta con una probabilidad del clasificador; ambas comparten la escala 0-100, pero su significado estadístico es distinto. Esta combinación es operativa y explicable, aunque una versión científica más fuerte debería calibrar ambos componentes y aprender los pesos sobre un conjunto de validación.

La aplicación Streamlit

src/app.py es el punto de entrada. Guarda la vista en query_params, ofrece cinco botones de navegación y delega el contenido en módulos de pantalla. Cada cambio de vista actualiza el parámetro y ejecuta st.rerun. La interfaz comparte estilos de tarjetas, estados y grids mediante ui_components.py.

Vista	Qué hace	Qué conviene enseñar
Inicio	Resumen de estado y accesos rápidos.	La idea global; evita centrarte en elementos heredados de extensión.
Configuración	Gmail, Telegram, monitor e hiperparámetros.	OAuth de solo lectura, secretos en .env.local y parámetros ajustables.

Estado de sesión y fallos controlados

Streamlit conserva en session_state la cuenta Gmail y los resultados importados para que no desaparezcan con cada rerun. La interfaz muestra mensajes específicos si faltan dependencias, credenciales, token o modelos. Si no existe un modelo válido, se prueba el del otro idioma y finalmente se entrena un modelo sintético mínimo para mantener la demostración.

Cómo explicarlo: el fallback mejora la disponibilidad de la demo, pero debe mostrarse con un aviso claro porque un modelo sintético de arranque no equivale a un modelo validado.


Gmail, monitorización y Telegram

OAuth y privacidad

La integración de Gmail usa un cliente OAuth de escritorio y el scope gmail.readonly. credentials.json identifica la aplicación y token.json almacena la autorización del usuario. Si el token ha caducado y contiene refresh_token, se renueva; si no existe, se abre el consentimiento. El código solo lista y descarga mensajes, no solicita permisos de modificación.

Monitor de correos

El monitor consulta Gmail mediante una query configurable, por ejemplo 'in:inbox newer_than:1d'. estado_monitor.json guarda los IDs ya vistos. En la primera ejecución puede marcar los mensajes existentes sin analizarlos, evitando una avalancha inicial de alertas. En ciclos posteriores solo procesa IDs nuevos, guarda el estado y espera el intervalo configurado.

	•	La vista Monitor permite una comprobación manual desde Streamlit.

	•	monitor_gmail.py puede ejecutarse una vez con --once o permanecer en bucle.

	•	El intervalo, query, límite, umbral, modo y pesos se leen de .env.local o del entorno.

	•	Los errores de un ciclo se registran y el bucle continúa; Ctrl+C detiene el proceso.

Alertas de Telegram

Cuando la puntuación supera el umbral, TelegramNotifier llama a la Bot API mediante HTTPS. El mensaje incluye nivel, puntuación, modo, remitente, asunto, número de URLs, hasta cinco señales activas y hasta tres enlaces recortados. Los valores se escapan como HTML para impedir que un remitente malicioso inyecte marcado en el mensaje.

Límite de privacidad: enviar remitente, asunto, señales y URLs a Telegram saca metadatos del entorno local. Debe ser opcional, informarse al usuario y evitarse con correos sensibles si no existe una base jurídica y una política de tratamiento.


¿El monitor contradice el enfoque solo web?

No, si se presenta correctamente. La aplicación web es la interfaz principal y el motor se ejecuta localmente. monitor_gmail.py es un proceso opcional de automatización que reutiliza módulos locales; no expone una API de análisis ni establece una arquitectura de cliente y servidor propia. Si se desea una versión estrictamente web, la comprobación manual de la vista Monitor cubre el mismo caso de uso sin mantener un proceso adicional.

Entrenamiento y evaluación

Carga flexible de CSV

dataset.py acepta rutas o archivos subidos, aumenta el límite de tamaño de los campos y usa DictReader. Busca una columna de etiqueta indicada o alternativas habituales. El texto puede venir completo o construirse con asunto y cuerpo; también añade remitente, destinatario, URLs y fecha cuando existen. Las filas vacías o sin texto se descartan.

Antes de entrenar, la interfaz resume cuántas filas válidas, phishing y legítimas hay por archivo. Esto permite detectar errores de columnas o un fuerte desequilibrio. Varios CSV se concatenan antes del ajuste para que TF-IDF construya un vocabulario común.

Entrenar

El usuario selecciona idioma, columnas y, opcionalmente, hiperparámetros personalizados. NeuralModelTrainer carga el modelo previo si existe. Si cambia el idioma o se proporcionan hiperparámetros, crea un clasificador nuevo pero conserva los textos y etiquetas anteriores. Después añade los nuevos CSV, ajusta el pipeline y guarda el .joblib.

Precaución: reentrenar sobre un modelo ya guardado acumula datos anteriores. Si se vuelven a subir los mismos CSV pueden duplicarse ejemplos. Para un experimento limpio hay que eliminar o versionar el modelo previo y registrar exactamente las fuentes.


Evaluar

La pestaña Evaluar carga un CSV que no modifica el modelo. Calcula predicciones, exactitud y la matriz de confusión: verdaderos positivos, verdaderos negativos, falsos positivos y falsos negativos. La interfaz actual no muestra directamente precision, recall y F1, aunque pueden calcularse a partir de la matriz.

precision = VP / (VP + FP)
recall = VP / (VP + FN)
F1 = 2 * precision * recall / (precision + recall)

En phishing, el recall es especialmente importante porque mide cuánto phishing real se detecta. Sin embargo, maximizarlo sin controlar precision puede llenar el sistema de falsas alarmas. La decisión adecuada depende del coste de cada error.

Comparar

La pestaña Comparar entrena en memoria hasta tres configuraciones sobre el mismo conjunto y las evalúa en un CSV de prueba común. Muestra accuracy y VP/VN/FP/FN. Los modelos comparados no se guardan automáticamente, lo que evita llenar el repositorio de artefactos experimentales.

Qué significan las métricas

Accuracy: proporción total de aciertos; puede engañar si las clases están desequilibradas.

Precision: de los correos marcados como phishing, cuántos lo eran realmente.

Recall: de todo el phishing real, cuánto logró detectar el modelo.

F1: media armónica de precision y recall; resume el equilibrio entre ambas.

Matriz de confusión: muestra los cuatro tipos de resultado y permite entender el coste de los errores.

El sistema analiza contenido potencialmente sensible. El diseño local reduce exposición, pero no elimina responsabilidades. Si Streamlit se ejecuta en otro equipo o se despliega en la nube, el límite de confianza cambia: el correo se procesa en ese host.

	•	credentials.json, token.json y .env.local deben permanecer fuera de Git.

	•	No se deben usar cuentas personales ni correos reales en una defensa pública.

	•	Telegram debe tratarse como salida externa de metadatos y mantenerse desactivado en demos sensibles.

	•	Los modelos joblib solo deben cargarse desde fuentes confiables: la deserialización puede ejecutar código.

	•	Los .joblib actuales almacenan textos de entrenamiento; deben revisarse antes de compartirlos públicamente.

	•	La clasificación es una ayuda a la decisión, no una orden automática de borrar o bloquear mensajes.

Decisiones de diseño que debes justificar

¿Por qué combinar reglas y aprendizaje supervisado?

Porque sus errores son distintos. Las reglas son transparentes y aprovechan cabeceras y HTML; el modelo reconoce patrones de texto aprendidos. El modo combinado conserva explicaciones y reduce la dependencia de una única técnica.

¿Por qué ejecutar el análisis en una sola aplicación?

Reduce complejidad, superficie de ataque, configuración y movimiento de datos. Para un TFG local no se necesita una API independiente. Si el sistema creciera a múltiples consumidores o alto volumen, entonces sí se evaluaría separar servicios.

¿Por qué un umbral de 45?

Es un umbral operativo del prototipo para exigir varias señales sin esperar a una puntuación extrema. No está calibrado de forma definitiva; debe ajustarse con datos representativos y el coste de FP/FN.

¿Por qué pesos 60/40?

Se prioriza ligeramente la trazabilidad heurística y se usa el modelo como complemento. Son configurables y no se presentan como óptimos; una mejora sería aprenderlos o calibrarlos sobre validación.

¿Por qué no consultar VirusTotal o reputación online?

Para mantener pruebas seguras, reproducibles y sin enviar URLs sensibles a terceros. Es una extensión futura, no una omisión desconocida.

Preguntas difíciles del tribunal

¿Esto es realmente una aplicación web si se ejecuta en local?

Sí. Streamlit sirve una interfaz web accesible desde el navegador. 'Local' describe dónde se ejecuta y dónde se procesan los datos, no el tipo de interfaz. No se defiende una SPA con API propia, sino una aplicación web Python autocontenida.

¿No existe siempre un servidor en Streamlit?

Internamente Streamlit usa HTTP para mostrar la UI, pero arquitectónicamente el proyecto no separa un cliente propio y un backend REST. La vista y el dominio pertenecen al mismo proceso y las funciones se invocan localmente.

¿MLP es deep learning?

Es una red neuronal feed-forward. Puede tener varias capas, pero en este trabajo se presenta como un clasificador neuronal ligero. No conviene equipararlo a transformers o a modelos profundos del estado del arte.

¿La puntuación combinada es una probabilidad?

No. Es un índice de riesgo ponderado que mezcla una puntuación experta y una probabilidad. Comparten escala, pero no interpretación estadística. La calibración queda como mejora.

¿Por qué una exactitud de entrenamiento cercana al 100 % no demuestra calidad?

Porque se evalúa sobre los mismos ejemplos usados para ajustar el modelo. Puede ser memorización. La evidencia válida debe venir de datos separados y, mejor aún, de otro periodo o fuente.

¿Qué error es más grave?

En seguridad suele preocupar más el falso negativo porque deja pasar phishing, pero demasiados falsos positivos generan fatiga y hacen que el usuario ignore alertas. El umbral debe equilibrar ambos costes.

¿Qué ocurre si el idioma se detecta mal?

La vista de detección agrupa todo lo que no sea inglés como español y usa un modelo alternativo si falta el adecuado. Los textos cortos pueden fallar; una mejora sería combinar detección de idioma, confianza y un modelo multilingüe.

¿Qué pasa si no hay modelos?

Se crea un modelo sintético de diez ejemplos para que la demo funcione. La interfaz avisa. Ese fallback no debe confundirse con un modelo validado.

¿Puede el sistema abrir un enlace peligroso?

No. Extrae y analiza cadenas de URL, pero no navega ni descarga la página. Esto reduce riesgo y también limita la información disponible.

¿Cómo protege Gmail?

Usa OAuth y gmail.readonly. El token se guarda localmente y no se modifica la bandeja. Para una demo se usa una cuenta de prueba y se protege el token.

¿Qué aporta el sistema frente a un filtro de Gmail?

No pretende reemplazarlo. Es una herramienta académica para inspección explicable, experimentación y entrenamiento. Gmail opera con infraestructura y señales de reputación mucho más amplias.

¿Cómo se añaden nuevas reglas?

Se implementan en el módulo de su familia, se exportan por signals.py, se registran en SignalBuilder, se asigna un peso en RiskScorer, se añade una explicación y se crea una prueba.

¿Por qué no se usa el HTML directamente en el modelo?

El modelo recibe texto normalizado; el HTML se reserva para reglas estructurales. Podría añadirse una representación específica, pero mezclar etiquetas crudas puede introducir ruido y riesgo de sobreajuste.

¿Por qué guardar modelos con joblib?

Serializa el pipeline completo y simplifica inferencia. Debe cargarse solo desde fuentes confiables y convendría versionar dependencias y separar datos de entrenamiento.

¿Cómo demostrarías mejora real?

Congelaría un conjunto de prueba independiente y temporalmente posterior, compararía heurística, MLP y combinado, reportaría intervalos o validación cruzada, y analizaría errores por tipo de ataque.

¿Qué harías primero para producción?

Autenticación, gestión de secretos, aislamiento de sesiones, logging seguro, modelo sin textos de entrenamiento, reputación controlada, calibración y evaluación con datos recientes.

¿El monitor elige hoy el modelo por idioma para cada mensaje?

La vista Detección sí. El servicio usado por el monitor carga primero el modelo español y después el inglés como fallback; por tanto, la selección por mensaje no está unificada todavía. Es una deuda técnica identificada.

¿Por qué siguen apareciendo archivos de backend y extensión en la rama?

Son restos de una iteración descartada. No forman parte del alcance que se defiende y deben eliminarse o aislarse antes de la entrega final para que repositorio, README y memoria sean coherentes.

¿La interfaz muestra precision, recall y F1?

La versión actual muestra accuracy y matriz de confusión. Las otras métricas se calcularon para el experimento documentado, pero la afirmación de que aparecen en la vista debe corregirse o implementarse.

¿Qué aspecto del trabajo demuestra más control?

La separación entre entrada, normalización, señales, puntuación, explicación y modelo; permite razonar sobre cada decisión, probarla y sustituir componentes sin rehacer todo el sistema.

Glosario para responder con precisión

SPF: autoriza qué servidores pueden enviar correo por un dominio.

DKIM: firma criptográficamente partes del mensaje y permite verificar integridad y dominio firmante.

DMARC: aplica una política basada en SPF/DKIM y su alineación con el dominio visible.

TF-IDF: pondera términos por su frecuencia en un documento y su rareza en el corpus.

N-grama: secuencia de una o varias palabras usada como característica.

MLP: perceptrón multicapa; red feed-forward con capas ocultas.

Precision: proporción de alertas de phishing que eran phishing real.

Recall: proporción del phishing real que fue detectado.

Falso positivo: correo legítimo marcado como phishing.

Falso negativo: phishing clasificado como legítimo.

OAuth: autorización delegada sin entregar la contraseña a la aplicación.

Punycode: codificación ASCII de dominios internacionalizados, a veces usada en homógrafos.

Calibración: ajuste para que una puntuación probabilística corresponda a frecuencias reales.

Sobreajuste: rendimiento excelente en entrenamiento pero pobre con datos nuevos.
